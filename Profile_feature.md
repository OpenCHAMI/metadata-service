# Profile Feature Plan for OpenCHAMI Metadata Service (Post-Fabrica)

## Summary

This plan introduces a Profile resource that works with the current Fabrica-generated, versioned API and the updated metadata pipeline. Profiles let sysadmins create isolated, testable variants of templates and metadata without impacting others. Profiles are selected via a backward-compatible NoCloud URL path segment, can expire, and are never deleted. The design includes parent-profile inheritance, per-node DefaultProfile, and server-side profile resolution in the cloud-init handlers.

## Problems to Solve

1. Conflicting edits to shared group metadata and templates cause lost updates and unintended cross-impact.
2. Sysadmins need a safe way to test changes that affect both metadata and cloud-config templates without affecting other admins or production behavior.
3. The NoCloud datasource must remain backward compatible for nodes that do not use profiles.
4. Profiles should not be deleted; they should expire and be cleaned up later.

## Constraints and Decisions

1. No profile discovery in /meta-data.
2. Profile names are arbitrary; ownership and ACLs will be added later via JWT.
3. Deletion should fail; profiles only expire.
4. Cross-group profile question removed (not needed for this iteration).
5. Profiles should never be deleted, only expired; cleanup jobs can be added later.
6. Per-node DefaultProfile is required.
7. Generated files are not edited directly; changes flow from resource definitions + fabrica generate.

## High-Level Design

### Data Model
Introduce a new Profile resource, separate from Group, using the versioned hub types under apis/. Each Profile references a Group and provides a variant of template and metadata. Profiles may inherit from a parent profile or from the default Group configuration.

### Selection Mechanism
Profiles are selected by a path-based URL segment in NoCloud URLs:

- Default behavior (no profile): ds=nocloud-net;s=https://metadata.example/metadata/
- Profile behavior: ds=nocloud-net;s=https://metadata.example/metadata/profile=alex/

This preserves backward compatibility.

### Expiration Semantics
Profiles are immutable in terms of deletion: deletion is blocked. Profiles can expire via an explicit expires_at or ttl_seconds. Expired profiles are ignored at runtime.

### DefaultProfile
DefaultProfile already exists in the versioned InstanceInfo hub type. If a profile is not specified in the URL, DefaultProfile applies; otherwise, default group behavior is used.

## Resource Design

### ProfileSpec
- groupRef: string (Group UID or name)
- parentProfile: string (optional, profile name)
- template: string (optional; if empty, inherit)
- metaData: map<string,string> (optional; merged over parent)
- expires_at: RFC3339 string (optional)
- ttl_seconds: int (optional; server computes status.expires_at)

### ProfileStatus
- expired: bool
- expired_at: RFC3339 string
- expires_at: RFC3339 string (computed when ttl_seconds used)

## Handler Behavior

### Profile Resolution
When serving /meta-data, /vendor-data, /user-data, /{group}.yaml:
1. Resolve profile from URL path: /profile=alex/…
2. If missing, use InstanceInfo.DefaultProfile (if set).
3. If profile is expired or missing, fall back to default Group behavior.
4. If profile exists:
   - Resolve parent chain to the root.
   - Merge metadata: parent first, child overrides.
   - Use child template if present; otherwise inherit parent template, ultimately default Group template.

### Vendor-Data Includes
When profile is active, include URLs should use the profile path:
- base: https://metadata.example/metadata/
- with profile: https://metadata.example/metadata/profile=alex/
- includes: https://metadata.example/metadata/profile=alex/{group}.yaml

### Deletion
All delete operations for Profile must fail with 405 or 409. This is enforced at the routing layer (not by modifying generated handlers).

## API Surface

### New Resource Endpoints
Generated by Fabrica:
- POST /profiles
- GET /profiles
- GET /profiles/{uid}
- PATCH /profiles/{uid}
- PUT /profiles/{uid}
- DELETE /profiles/{uid} (blocked)

### Existing Endpoints (Backward Compatible)
- /meta-data
- /vendor-data
- /user-data
- /{group}.yaml
- Optional profile path variants:
  - /profile={name}/meta-data
  - /profile={name}/vendor-data
  - /profile={name}/user-data
  - /profile={name}/{group}.yaml

## Implementation Steps

1. Add Profile hub type under apis/cloud-init.openchami.io/v1/profile_types.go and register it in apis.yaml.
2. Add Profile resource definition under pkg/resources/profile/ with Spec and Status fields (expiration + parent validation).
3. Ensure InstanceInfoSpec DefaultProfile is present in pkg/resources/instanceinfo and mapped through storage adapters.
4. Implement profile resolution helper in pkg/handlers/metadata.go and extend handlers to apply profile overrides.
5. Update cloudinit_routes and storage adapter to resolve profiles and register profile-prefixed routes.
6. Modify vendor-data handler to emit profile-prefixed include URLs when profile is active.
7. Block Profile delete operations in router layer.
8. Run fabrica generate (local binary) and update client usage documentation.
9. Add tests for profile resolution, expiration, and include URL behavior; update docs and demo scripts.

## Tradeoffs

### Separate Profile Resource vs Embedded in Group
- Separate resource is chosen because it eliminates concurrent edit conflicts, supports per-profile permissions later, and scales without bloating Group size.
- Embedded profiles would reintroduce conflicts when multiple admins patch the same Group.

### Path-Based Profile vs Query Params
- Path-based avoids URL composition issues with NoCloud’s base URL and is easier to route.
- Query params could be supported later but are not required.

### Expiration vs Deletion
- Expiration ensures auditability and prevents accidental loss.
- Cleanup is deferred to a future maintenance job.

## Risks and Mitigations

- Profile chain cycles: enforce parent chain validation to prevent cycles.
- Profile expiration time ambiguity: define precedence; expires_at overrides ttl_seconds.
- Unauthorized profile usage: ownership enforcement deferred to JWT-based auth.
- UID vs name lookups: define profile lookup strategy (name for URL paths; UID for API storage) and enforce mapping in adapters.

## Deliverables

- Profile resource type + generated handlers and client
- Updated cloud-init handlers with profile selection and backward-compatible routing
- InstanceInfo DefaultProfile support in storage adapter and handlers
- Documentation updates and demo script with profile examples

## Open Questions (If Any)
- Decide whether profile lookup should accept UID in URL paths or only names.
